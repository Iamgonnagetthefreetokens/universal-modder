# Bridge protocol v1 — `um-bridge`

Normative. The Python reference (`fakes/bridge.py`) and the Rust crate (`bridge/`) both implement exactly
this document; `bridge/testdata/vectors.json` (generated by the Python side, consumed by the Rust tests)
holds the byte-level and coordinate test vectors, so a disagreement is a failing test rather than a
mystery. Everything is **little-endian**; `f32` is IEEE-754; all offsets are bytes.

Two transports, on purpose:

| Transport | Carries | Why |
|---|---|---|
| **Control channel** — TCP, `127.0.0.1`, line-delimited ASCII | handshake, camera, terrain revision, input, focus, heartbeats, wake-up notifications | ordered, reliable, human-readable (`nc 127.0.0.1 47811` shows the traffic), trivial to version, and small enough (a few kB/s) that TCP framing costs nothing |
| **Shared regions** — file-backed, double-buffered | the bulk data: guest entity/event state, host heightfield, guest framebuffer | state and pixels are large and loss-tolerant (latest wins); a file mapping is the same mechanism the Minecraft×GTA V reference used for frames, minus the `CreateFileMapping` plumbing, and it needs no dependencies on either side |

Deliberately **not** used: the games' own netcode. RecWars' UDP/WebRTC layer (`src/net.rs`) exists for
players; the bridge must never touch it, because that path is what keeps a match honest.

## 1. Files and the run directory

Both sides agree on a run directory:

| Platform | Default |
|---|---|
| Linux | `$XDG_RUNTIME_DIR/um-bridge/veloren-recwars` (falls back to `/tmp/um-bridge/veloren-recwars`) |
| Windows | `%LOCALAPPDATA%\um-bridge\veloren-recwars` |

The host creates it and passes it in `HELLO`; the guest refuses to start if it cannot write there (this
makes "two Veloren windows fighting over one region" impossible to reach by accident — the second writer
sees a live writer bit and exits with an error). Files: `state.region`, `terrain.region`, `frame.region`.
An attacker with write access to that directory can feed the game bogus bytes; the bridge therefore only
ever *reads* what it validates (CRC + sequence + size) and never executes anything from a region, and the
directory is only writable by the user.

## 2. Region file format

A region is a fixed-size file: a 64-byte header followed by `slots` (2) payload slots.

### 2.1 Header (64 bytes)

| Offset | Type | Field | Meaning |
|---|---|---|---|
| 0 | `[u8;4]` | `magic` | `55 4D 42 52` = `"UMBR"` |
| 4 | `u16` | `version` | protocol version, `1` |
| 6 | `u16` | `kind` | `1` state, `2` terrain, `3` frame |
| 8 | `u32` | `payload_size` | bytes per slot |
| 12 | `u16` | `slots` | `2` |
| 14 | `u16` | `hdr_size` | `64` |
| 16 | `u64` | `seq` | committed sequence, starts at 1; `0` = no data yet |
| 24 | `u16` | `slot` | which slot the committed payload is in (`seq % 2`) |
| 26 | `u16` | `flags` | bit0 writer alive, bit1 reset requested |
| 28 | `u32` | `payload_len` | bytes used in the slot (≤ `payload_size`) |
| 32 | `u32` | `crc32` | CRC-32 (IEEE, as in zlib) of `payload[..payload_len]` |
| 36 | `u64` | `write_ts_us` | writer's monotonic clock, µs |
| 44 | `u32` | `writer_pid` | writer's OS pid |
| 48 | 16 bytes | reserved | zero |

### 2.2 Commit protocol (single writer, single reader, no locks)

Writer:
1. `pwrite(fd, payload, 64 + slot*payload_size)` with `slot = seq % 2` — never the slot the reader is
   currently reading, because that is the other slot (`(seq-1) % 2`).
2. One 28-byte `pwrite` at offset 16 carrying `seq+1, slot, flags, payload_len, crc32, write_ts_us`. This is
   the commit point: readers take the header as the truth, so the payload is finished before it is
   published.
3. Bump local `seq`, flip `slot`.

Reader:
1. Read the 44-byte header prefix (offsets 0–44).
2. If `seq == 0` → `Empty`. Validate `magic`, `version`, `kind`, `payload_len ≤ payload_size`.
3. Read `payload[..payload_len]` from slot `slot`.
4. Re-read the commit prefix (offset 16, 28 bytes). If it changed, or the CRC fails, count a `torn` read and
   retry (default 8 attempts, then return `Busy`).
5. Return the payload. `write_ts_us` gives the age of the data, which is what the host uses to fade or
   freeze a stale guest frame instead of pretending it is live.

Why this is safe enough: the commit is a *single* `pwrite` of 28 bytes, which hits the page cache as one
syscall, and both the sequence check and the CRC catch anything the kernel, a partial write, or a dead
writer leaves behind. It is not a lock-free guarantee in the academic sense — `mmap` + a real seqlock is the
documented optimization (`docs/ARCHITECTURE.md` §5) and it is only worth doing for the frame region.

Writer liveness: the writer sets bit0 of `flags` on creation and clears it on clean shutdown `BYE`. A peer
that finds bit0 set refreshes `writer_pid`/`write_ts_us` staleness: `writer alive` + no commit for >2 s =
wedged writer → the reader logs once and freezes on the last good payload.

### 2.3 `kind = 1`, state region (guest → host)

`payload = StateHeader (32 B) | Entity × ent_count (40 B) | Event × event_count (24 B)`

StateHeader:

| Offset | Type | Field | Meaning |
|---|---|---|---|
| 0 | `u32` | `tick` | guest simulation tick |
| 4 | `u32` | `game_time_ms` | guest game clock, ms |
| 8 | `u16` | `ent_count` | ≤ 512 |
| 10 | `u16` | `event_count` | ≤ 64 |
| 12 | `u16` | `focus_ent` | entity id the host should follow; `0xFFFF` none |
| 14 | `u16` | `flags` | bit0 local player alive, bit1 paused, bit2 match over |
| 16 | `f32` | `player_x` | local player position, guest units |
| 20 | `f32` | `player_y` | |
| 24 | `f32` | `cam_x` | guest view centre, guest units |
| 28 | `f32` | `cam_y` | |

Entity (40 B):

| Offset | Type | Field | Notes |
|---|---|---|---|
| 0 | `u32` | `id` | stable per entity |
| 4 | `u8` | `kind` | 0 none, 1 player, 2 tank, 3 hovercraft, 4 hummer, 5 bot, 6 projectile, 7 explosion, 8 pickup |
| 5 | `u8` | `team` | |
| 6 | `u8` | `flags` | bit0 alive, bit1 firing, bit2 local player, bit3 selected by host |
| 7 | `u8` | pad | |
| 8 | `f32` | `x`, `y`, `z` | guest units; `z` is the height the guest believes it is at (`0` = unknown, host re-derives) |
| 20 | `f32` | `angle` | hull angle, radians, screen convention (see `MAPPING.md`) |
| 24 | `f32` | `turret_angle` | |
| 28 | `f32` | `vx`, `vy` | units/s |
| 36 | `f32` | `hp_frac` | 0..1 |

Event (24 B):

| Offset | Type | Field | Notes |
|---|---|---|---|
| 0 | `u8` | `kind` | 1 fire, 2 hit, 3 explosion, 4 kill, 5 spawn, 6 pickup, 7 self-destruct |
| 1 | `u8` | `flags` | |
| 2 | `u16` | `arg16` | radius (units) for explosions, weapon id for fire |
| 4 | `u32` | `t_ms` | guest game time |
| 8 | `f32` | `x`, `y`, `z` | guest units |
| 20 | `f32` | `arg` | power/damage |

Events are **newest-last** in a ring of the last 64; the host tracks the last processed `(t_ms, kind, x, y)`
key, so a restart of either side replays nothing (there is no event id, on purpose: the events are
cosmetic-plus-gameplay hints that must not be applied twice, and the region is republished whole every tick
anyway).

### 2.4 `kind = 2`, terrain region (host → guest)

`payload = TerrainHeader (32 B) | Cell × nx*ny (8 B)`, row-major, `(0,0)` first = the corner at
`(origin_x, origin_y)` with the lowest `x`/`y`.

TerrainHeader:

| Offset | Type | Field | Meaning |
|---|---|---|---|
| 0 | `f32` | `origin_x` | Veloren world metres, min corner |
| 4 | `f32` | `origin_y` | |
| 8 | `f32` | `cell_m` | metres per cell (`8.0` default; `nx=ny=64` ⇒ a 512 m square) |
| 12 | `u16` | `nx`, `ny` | 64 × 64 default, ≤ 128 |
| 16 | `f32` | `tile_m` | metres per guest tile (`8.0`) — the guest map is built from this |
| 20 | `f32` | `sea_level` | metres; host reports its own sea level |
| 24 | `u32` | `revision` | bumps when the covered area or the contents change |
| 28 | `u32` | `flags` | bit0 fresh, bit1 partial (edge of loaded chunks), bit2 has water |

Cell (8 B):

| Offset | Type | Field | Meaning |
|---|---|---|---|
| 0 | `f32` | `height_m` | ground height at the cell centre |
| 4 | `u8` | `kind` | 0 unknown/void, 1 water, 2 shallow, 3 sand, 4 grass, 5 rock, 6 cliff (wall), 7 snow |
| 5 | `u8` | `flags` | bit0 spawnable, bit1 has liquid |
| 6 | `u16` | pad | |

### 2.5 `kind = 3`, frame region (guest → host)

`payload = FrameHeader (32 B) | pixels (height × stride)`, pixels **BGRA8**, top row first, straight alpha.

FrameHeader:

| Offset | Type | Field | Meaning |
|---|---|---|---|
| 0 | `u16` | `width`, `height` | published size (may be smaller than the game's window) |
| 4 | `u32` | `stride` | `width * 4` |
| 8 | `u8` | `format` | 1 = BGRA8 |
| 9 | `u8` | `flags` | bit0 alpha present, bit1 letterboxed |
| 10 | `u16` | `scale_permille` | published size ÷ window size × 1000 |
| 12 | `u32` | reserved | |
| 16 | `u64` | `publish_ts_us` | guest monotonic µs |
| 24 | `u32` | `game_tick` | |
| 28 | `u32` | `reserved2` | |

The region is recreated when the geometry changes (window resize, scale change); `FRAME` on the control
channel always precedes the first commit in the new geometry so the host can re-allocate its texture.

## 3. Control channel

TCP, `127.0.0.1:47811` by default (`bridge.port` cvar / `--bridge-port`). The guest **listens** (it is the
longer-lived process in the intended workflow: start RecWars, then Veloren), the host connects. Lines are
ASCII, `\n`-terminated, fields space-separated `key=value`, the first token is the message type. Unknown
keys are ignored (forward compatibility); unknown *messages* are ignored but counted.

| Type | Direction | Rate | Payload |
|---|---|---|---|
| `HELLO` | host → guest | once | `v=1 role=host app=veloren pid=… proto=1 run_dir=…` |
| `WELCOME` | guest → host | once | `v=1 role=guest app=recwars pid=… tick_hz=60 state_region=… frame=640x360` |
| `CAM` | host → guest | 20 Hz | `t=… x=… y=… z=… yaw=… pitch=… fov=… sx=… sy=…` (Veloren metres, radians) |
| `MAP` | host → guest | on change | `rev=… cells=64 cell_m=8.000 origin_x=… origin_y=…` (bytes in `terrain.region`) |
| `FRAME` | guest → host | on change | `w=… h=… scale=… fmt=1` |
| `NOTIFY` | guest → host | per state commit, ≤ 30 Hz | `kind=state seq=…` |
| `FOCUS` | host → guest | on toggle | `on=1` / `on=0` |
| `IN` | host → guest | per event | `a=fire d=1 t=…` |
| `MOUSE` | host → guest | per event | `t=… dx=… dy=…` |
| `PING`/`PONG` | both | 1 Hz | `t_us=…` (echoed by the responder → RTT and clock offset estimate) |
| `HB` | both | 2 Hz | `t_ms=…` |
| `BYE` | both | once | `reason=…` |

Action names (the fixed set, mapped 1:1 onto RecWars' `ClientInput`, `src/input.rs:15`):
`left right forward back turret_l turret_r prev_weapon next_weapon fire mine self_destruct horn`.

The host translates its own key bindings into actions, so the guest never learns Veloren's controls and the
guest keeps its own key handling when the bridge is off.

## 4. Versioning and failure

- `v` must match the receiver's `PROTOCOL_VERSION` (`1`) or the handshake fails with
  `BYE reason=version` — a patch mismatch between the two games must be loud, not subtle.
- Message field sets are open: add keys, never renumber. Region layouts are not open: a layout change bumps
  `version` and the region header's `version` must match, or the reader rebuilds the file.
- Total silence (no control line *and* no region commit) for 2 s = peer dead (watchdog). The host freezes
  the last frame and shows `guest offline`; the guest drops back to normal play and ignores bridge input.
  Neither side kills the other's process — that is the user's job (`um win kill <pid>`).
